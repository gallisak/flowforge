# Технічне завдання
## Тестовий пет-проект №8: FlowForge — Multi-tenant Durable Workflow Platform
### (надійна черга на Postgres, durable execution, ізоляція тенантів, безпечне виконання користувацьких кроків)

---

## 1. Мета

Завдання перевіряє здатність довести до production-якості систему, яка виконує **чужі**
сценарії від імені багатьох клієнтів: користувач описує workflow як послідовність кроків
(HTTP-виклик, трансформація даних, пауза, лог), а платформа гарантує, що кожен крок виконається
правильну кількість разів, навіть якщо воркер впав, інстансів кілька, а один із клієнтів
навмисно або випадково перевантажує систему чи намагається вийти за межі свого тенанта.

Кандидат стартує **не з чистого аркуша**: надається працюючий, але не готовий до продакшену
репозиторій (розділ 3). Потрібно розібратись у наявному коді, знайти проблеми, які в ньому
закладені, виправити їх, довести кожну тестом і розвинути платформу далі.

**Що перевіряємо:**
- Семантику черги задач на Postgres: атомарне захоплення, lease/heartbeat, відновлення після
  падіння воркера, повторні спроби, "отруйні" задачі
- Durable execution: чекпоінти по кроках, відновлення з місця зупинки, ідемпотентність
  побічних ефектів, прив'язка виконання до версії workflow
- Мультитенантну ізоляцію на кількох рівнях (код, БД) і справедливий розподіл ресурсів між
  тенантами ("шумний сусід")
- Безпеку виконання користувацької логіки: SSRF, пісочниця для виразів, автентичність webhook-ів
- Розподілений планувальник: рівно одне спрацювання на розклад при кількох інстансах, часові
  пояси, DST, політика пропущених запусків
- Спостережуваність і доказову інженерію: чи вміє кандидат довести наявність дефекту
  відтворюваним тестом, а не лише описати його словами
- Вміння читати чужий код, не довіряти "зеленому" CI й безпечно вносити зміни в систему, що
  вже працює

## 2. Стек технологій

| Шар | Технологія |
|---|---|
| Backend | NestJS (TypeScript): HTTP API, окремий процес-воркер, планувальник |
| Черга / стан | PostgreSQL (черга задач у БД: `FOR UPDATE SKIP LOCKED`, lease, advisory-локи — на вибір кандидата, з обґрунтуванням) |
| ORM | TypeORM (наявний) — допускається raw SQL там, де це виправдано |
| Frontend | Next.js (App Router, TypeScript) |
| Real-time | SSE або WebSocket — на вибір, з обґрунтуванням |
| Спостережуваність | Структуроване логування з кореляційним ID, `/metrics` (Prometheus-формат), health/readiness |
| Контейнеризація | Docker + docker-compose (API, мінімум 2 воркери, Postgres, фронтенд) |

Додаткові брокери (Redis, Kafka тощо) **не потрібні**: завдання навмисно обмежене Postgres, щоб
оцінювати розуміння семантики черги, а не вміння підключити інфраструктуру. Використання
додаткових бібліотек (sandbox, SSRF-захист, метрики) дозволене — вибір оцінюється.

## 3. Стартовий репозиторій

Кандидат отримує посилання на приватний репозиторій і працює далі в ньому (форк або окрема гілка).

### 3.1 Що вже надано

- `apps/api` — NestJS-застосунок: тенанти й автентифікація за API-ключем, CRUD workflow,
  запуск виконання вручну, вхідні webhook-и, планувальник cron, окремий процес-воркер
- Виконавці кроків `http`, `transform`, `log`, `delay` і шаблонізатор `{{ input.x }}`
- Таблиці `jobs`, `executions`, `step_runs` (останні фіксують перебіг кроків)
- `apps/frontend` — Next.js: ввід API-ключа, список workflow, сторінка виконання
- `docker-compose.yml`, CI (лінт, типчек, тести), `.env.example`, README
- Набір тестів: частина з них перевіряє важливу поведінку, частина — ні

Базові сценарії працюють: створити тенанта, описати workflow, запустити, побачити результат.

### 3.2 Що потрібно знайти й виправити самостійно

У коді закладено понад вісім проблем різних категорій. Точні місця **не розкриваються** —
пошук є частиною завдання. Категорії:

- Ізоляція даних між тенантами
- Коректність черги задач за наявності кількох воркерів
- Поведінка системи при аварійному завершенні воркера
- Безпека виконання кроків: що може зробити тенант через кроки різних типів
- Автентичність і повторна доставка вхідних webhook-ів
- Поведінка планувальника при кількох інстансах, перезапуску та різних часових поясах
- Властивості виконання, які не відповідають очікуванням користувача платформи (що відбувається
  з уже виконаними кроками при повторі, що — зі зміною workflow під час виконання, що — з
  паузами при перезапуску)
- Клієнтський код, який з часом деградує
- Тести, які проходять незалежно від того, чи дотримано поведінку, заявлену в їхній назві

Кожну знахідку потрібно: **(а)** відтворити автоматизованим тестом або скриптом (до виправлення
— червоний, після — зелений), **(б)** виправити, **(в)** описати в README: що, чому небезпечно,
як відтворити, як виправлено, які були альтернативи.

### 3.3 Основне завдання поверх стартового коду

1. **Надійна черга.** Атомарне захоплення задач; lease із продовженням (heartbeat) та
   автоматичним поверненням у чергу задач, чий воркер зник; повторні спроби з експоненційним
   backoff і jitter, розрізнення "повторювана / неповторювана" помилка; ліміт спроб і окремий
   стан для задач, що вичерпали його; коректне завершення воркера (graceful shutdown) без
   втрати поточних задач.
2. **Durable execution.** Виконання продовжується з першого незавершеного кроку, а не з нуля;
   результат завершеного кроку не обчислюється повторно. Для кроків із побічними ефектами
   (`http`) кожна спроба має стабільний ключ ідемпотентності, який передається отримувачу.
   Виконання працює зі **знімком** версії workflow, зафіксованим на момент старту.
3. **Довговічні таймери.** Крок `delay` не утримує слот воркера й переживає перезапуск
   (персистентний час пробудження).
4. **Ізоляція тенантів у глибину.** Окрім перевірок у коді — захист на рівні Postgres (Row-Level
   Security або еквівалент) із доказом тестом, що запит без контексту тенанта нічого не бачить.
   Ліміти на тенанта: кількість одночасних виконань, розмір черги, частота запитів.
5. **Справедливе планування.** Один тенант, який поставив у чергу десятки тисяч задач, не повинен
   суттєво збільшувати затримку виконання задач інших тенантів. Показати вимірюванням.
6. **Безпечне виконання кроків.** Крок `http` не повинен мати доступу до внутрішніх ресурсів
   інфраструктури (включно з випадками редиректів і підміни DNS-відповіді); обмеження на розмір
   відповіді та час виконання. Крок `transform` не повинен виконувати довільний код хоста; обрана
   модель (обмежена мова виразів, ізольоване виконання з лімітами часу/пам'яті тощо) обґрунтовується
   в README.
7. **Вхідні webhook-и.** Перевірка підпису над тілом так, як воно надійшло; порівняння без витоку
   інформації про час; вікно допустимого часу та захист від повторної доставки; ротація секрету
   без простою; повторна доставка однієї й тієї самої події не створює другого виконання.
8. **Планувальник.** Одне спрацювання на розклад незалежно від кількості інстансів; коректні часові
   пояси та перехід на літній/зимовий час; конфігурована політика для запусків, пропущених під час
   простою (пропустити / виконати один раз / виконати всі).
9. **Вихідні події.** Після завершення виконання платформа надсилає підписане сповіщення на
   endpoint тенанта з гарантією "щонайменше один раз" через транзакційний outbox і повторні спроби.
10. **Спостережуваність.** Один кореляційний ID наскрізь: запит → виконання → задача → крок →
    вихідний запит. Метрики: глибина черги за тенантом, затримка захоплення, тривалість кроків,
    кількість повторів, кількість задач, що вичерпали спроби.
11. **Frontend.** Сторінка виконання з оновленням у реальному часі, що коректно поновлюється після
    розриву зʼєднання й не витікає ресурсами; форма створення/редагування workflow з валідацією;
    список виконань із курсорною пагінацією й фільтром за статусом; стани loading/empty/error.

## 4. Нефункціональні вимоги

- Жодна операція, що змінює стан у кількох таблицях, не залишає систему в проміжному стані при
  падінні процесу посередині
- Усі зовнішні виклики мають таймаути; жоден вхід від тенанта не може призвести до необмеженого
  споживання пам'яті чи часу воркера
- Валідація вхідних даних на межі системи; помилки не розкривають внутрішні деталі
- Секрети не потрапляють у логи й відповіді API
- Конфігурація через `.env`, наявний `.env.example` актуальний
- CI (лінт, типчек, тести) має лишатися зеленим; будь-яка зміна наявних тестів обґрунтовується в README

## 5. Архітектурні вимоги

- Для кожного з пунктів 3.3.1–3.3.8 у README — короткий запис рішення: які варіанти розглядались,
  що обрано, чому, які обмеження лишились
- Явно описана модель гарантій виконання: що гарантується (at-least-once / at-most-once /
  effectively-once) для кроку, для виконання, для вихідної події — і за яких умов
- Діаграма потоку: тригер → виконання → задача → крок → результат, з позначенням меж транзакцій
- Індекси в БД для запитів захоплення задач, списків виконань за тенантом, пошуку за ключами
  ідемпотентності; пояснення, як перевірено, що вони використовуються (план запиту)

## 6. Тестування

- Unit-тести: розрахунок backoff, валідація визначення workflow, мова виразів/пісочниця,
  перевірка підпису webhook, обчислення наступного спрацювання cron для різних часових поясів
  (включно з датами переходу на літній час)
- Інтеграційні тести на реальному Postgres:
  - N воркерів і M задач — кожна задача виконана рівно один раз
  - воркер примусово завершено посередині кроку — задачу підхоплено, завершені кроки не
    виконуються повторно, зовнішній побічний ефект стався один раз
  - два інстанси планувальника — одне спрацювання на розклад
  - тенант A не бачить і не може змінити дані тенанта B (включно з запитами в обхід шару сервісів)
- Тести безпеки: спроби SSRF (loopback, приватні діапазони, службові адреси хмарних провайдерів,
  редирект на внутрішню адресу), спроби виходу з пісочниці, повторна доставка webhook, підпис
  із зміненим тілом
- Навантажувальний сценарій для справедливого планування з результатами у README
- Тести, що відтворюють кожну знайдену в стартовому коді проблему
- Наявні тести лишаються зеленими або їхня зміна обґрунтована

| Документація, обґрунтування рішень, DX | 5% |
